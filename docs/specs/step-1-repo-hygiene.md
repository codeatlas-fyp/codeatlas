### Commit-message and branch rules (`check_commit_msgs.py`)

- **Branch:**
  - Pattern: `^(develop|(feature|fix|docs)/[a-z0-9]+(-[a-z0-9]+)*)$`.
  - `develop` stays allowed so the release PR `develop → main` passes.
- **Commit subject:** every non-merge commit in `base..head` must match
  `^(feat|fix|docs|chore|test|refactor)(\([a-z0-9-]+\))?: \S.*$`.
  - The scope is optional (Q2).
  - A trailing ` (#n)` is allowed but not required. GitHub may add `(#<PR>)` to squash commits on
    `develop`, and those commits are checked again by the `develop → main` PR (Q3).
- **Functions:**
  - `check_branch(name: str) -> str | None`
  - `check_subject(sha: str, subject: str) -> str | None`
  - `main(argv: list[str]) -> int`
  - Each check returns an error message or `None`. `main` prints the errors and returns 0 or 1.
- **Unchanged:**
  - The git command (`git log --no-merges --format=%h %s base..head`).
  - The CLI arguments and the `::error::` output.
  - The script still runs only on `pull_request` events.

## Acceptance criteria

**Checker (automated):**

- **AC1** Given a commit subject `feat(schema): add evidence models`, `fix: handle empty
  changelog` or `docs(spec): add step 1 spec (#3)`, when the check runs, then it passes.
- **AC2** Given a subject `CA-4: add parser`, `Add parser`, `feature: add parser`, `feat:add
  parser` or `feat(Schema): x`, when the check runs, then it fails with one `::error::` line
  naming the commit.
- **AC3** Given the branch `feature/repo-hygiene`, `fix/ci-cache`, `docs/sandbox-guide` or
  `develop`, then the branch check passes. Given `feature/CA-4-parser`, `Feature/x`,
  `feature/Repo_Hygiene`, `hotfix/x` or `main`, then it fails.
- **AC4** Given a range with one good and one bad commit, the exit code is 1 and only the bad
  commit is reported. Given only good commits, the exit code is 0. Merge commits are ignored.

**Repository and CI:**

- **AC5** Given the step 1 PRs, when CI runs, then the `ci` job is green (`pre-commit`,
  `lint-imports`, `mypy`, `pytest`).
- **AC6** Given `.coverage` and `bundles/x.json` in the working tree, `git status` does not
  show them.

**Manual checks, recorded in the PR description:**

- **AC7** Given a scratch line `import httpx` added to `src/codeatlas/evaluate/verdict.py`, when
  `uv run lint-imports` runs locally, then it fails naming K1 or K3. The line is then removed.
- **AC8** Given a staged file containing a dummy secret in a well-known token format, when
  `pre-commit run gitleaks` runs, then it fails. The file is not committed.
- **AC9** After PR 1b: `CODEOWNERS` has no placeholders, and GitHub's CODEOWNERS view shows no
  errors. `CONTRIBUTING.md`, the PR template and `CLAUDE.md` contain no `CA-<n>` and no R-IDs.

## Found during implementation

- **Q5 resolved from the docs.**
  - import-linter: "the top level configuration must have `include_external_packages = True`"
    to forbid external packages
    (https://import-linter.readthedocs.io/en/stable/contract_types/forbidden/). K3 is included.
  - gitleaks: hook id `gitleaks` (language `golang`, entry
    `gitleaks git --pre-commit --redact --staged --verbose`), from the gitleaks repository's
    `.pre-commit-hooks.yaml`; pinned to tag `v8.30.1`, the latest `v8.*` tag on 2026-10-07.
- **gitleaks scans staged changes only.** In CI, `pre-commit run --all-files` stages nothing, so
  the hook passes without scanning. Secrets are caught on laptops at commit time. A real CI
  secret scan is a follow-up for step 15 (§16 asks for gitleaks in CI too).
- **First pre-commit run builds gitleaks with Go.** It took about 4 minutes locally. CI pays this
  on every run until a pre-commit cache is added (step 15).
- **The test file runs `git` through `subprocess`**, so `tests/**` also ignores S603 and S607,
  not only S101.
- **ruff formats Markdown code blocks.** The verbatim mid-evaluation spec would be reformatted by
  the `ruff format` hook. PR 1b must exclude `docs/specs/mid-eval-spec.md` from ruff format.
